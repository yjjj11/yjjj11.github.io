## 场景：为什么需要它

在某段时间窗口内频繁交易的监控里，为每一个证券维护一个时间队列，存放对该券每次买入/卖出操作的结构体（金额、方向、数量、时间戳）。每次新交易消息进来，把操作信息加入队列；同时遍历可执行的监控，检查带时间窗口要求的监控时，就得对窗口内的操作数、总金额做统计，自然要排除过期数据。

一进一出，看起来简单。但**每次等监控触发了才去排除过期数据会拖慢流程**，而且多个监控、每个都要去重过期数据，速度很慢。

最初的想法：加一个后台线程定时处理过期数据。但**定时时间非常小，会极大加剧数据放入时的锁竞争**——不可取。于是想到了 SPSC 无锁缓冲区。

## 为什么 SPSC 可以不加锁

SPSC（Single Producer Single Consumer）只有一个生产者和一个消费者。**生产者只改变写下标，消费者只改变读下标，两者并不冲突**，理论上完全不用加锁。

但真正要解决的问题不是锁，而是**编译器优化**：

1. **指令重排**：原来是"先写数据再移动下标"，可能被重排成"先移动下标再写数据"——消费者读到的是垃圾数据；
2. **寄存器缓存**：下标可能被优化到寄存器，更新对另一线程不可见。

`Atomic` 变量强制刷回内存、禁止乱序，两个线程能第一时间看到数据更新；又因为无竞争不需要加锁，淘汰过期数据的速度大幅提升，监控也无需逐个淘汰。缺点：定时时间依旧很短、会增加 CPU 占用。

## 七个优化方向

**1. 读写下标分离缓存行（防伪共享）**

如果两个下标在不同缓存行，消费者读自己的 read 下标可以一直从 CPU 缓存读——只要该缓存行不被换出，就一直不用走内存，速度很快。但如果两个下标放一起，生产者移动 write 下标会让整个缓存行变脏（包括 read），消费者要读自己的 read 时发现该缓存行被其他线程改过而失效，必须触发缓存一致性协议：让生产者刷回内存后自己再重新读入。**伪共享是隐形杀手，把两个下标对齐到不同缓存行。**

**2. 分支预测提示**

"读追上写"的判断实际上很少成立，可以用 `[[unlikely]]` 提示编译器优化分支。

**3. 指令预取（prefetch）**

缓冲区内部存放的结构体类型统一，下标跳转的字节数统一，可以配合指令预取提前把后续数据搬入缓存，降低读取延迟。

**4. 正确的内存序**

自己下标的读用 `relaxed`，读别人的用 `acquire`，写自己的用 `release`——在保证正确性的前提下尽量放宽内存序，避免不必要的同步开销。

**5. 调度优先级**

提高读写两个线程的调度优先级、延迟执行时间片，防止上下文频繁切换带来的抖动。

**6. rdtsc 打点计时**

用 `rdtsc` 读 CPU 上电以来的时钟周期数来打点计时，避免 `high_resolution_clock` 频繁调用——它的调用开销本来就远大于 rdtsc，在高频路径上会放大整体延迟。

**7. 零拷贝**

不把数据真实存入 SPSC，只 push 对应数据的**结构体指针**，消费时通过指针访问数据——省去一次拷贝。代价是要管理好对象的生命周期。

## 总结

SPSC 无锁环形缓冲区是"无锁 = 无同步开销"的典型代表：锁被消除后，真正的敌人变成编译器与 CPU 缓存。伪共享、内存序、指令重排、预取——把这些细节逐个吃透，才能写出真正高吞吐的并发数据结构。
