## 一面 · CPU 占用到 100% 的可能原因与排查？

**可能原因**：
1. 死循环 / 逻辑 BUG：代码死循环、递归无终止、自旋锁循环、无意义轮询；
2. 频繁上下文切换：大量线程频繁抢占、锁竞争激烈；
3. 计算密集型任务：大量计算、序列化/反序列化、大数据遍历；
4. 系统资源争抢：磁盘 IO 卡死、文件句柄打满、恶意进程空转、网络流量爆炸导致的中断。

**排查工具**：
```bash
ps -aux --sort=-pcpu | head -10   # 找出 CPU 最高的进程 PID
ps -mp PID -o THREAD,tid,time      # 导出该进程所有线程 CPU 占用
pstack PID                         # 打印所有线程当前执行的代码
top                                # 看系统各项指标
```

`top` 里几个关键指标的含义：
- **us（用户态占用）高** → 查业务代码（自己程序的问题）；
- **sy（内核态 CPU）高** → 查内核 / 锁 / 网络 / 系统调用；
- **wa（磁盘 IO）高** → IO 阻塞导致进程频繁重试拉高 CPU；
- **si（软中断）高** → 最常见是网络流量爆炸：大量短连接、高并发小包、网络风暴。

## 一面 · 给你一个接口优化延迟，怎么考虑？

优化方向分五大块：**网络、DB、架构与语言、自身代码计算、锁竞争与线程排队**。先定位瓶颈：加链路耗时埋点，拆分接口每一步耗时，看耗时主要在哪一块。

- **网络层**：减少网络往返——缓存热点 RPC 结果、合并请求；就近部署、内网调用加快网络速度；
- **数据库层**：索引优化；批量查询替代循环单条查询；热点数据用 Redis 缓存；避免长事务拆成小事务；数据库连接池连接复用；
- **代码与业务层**：耗时计算异步化，非强依赖的逻辑丢工作线程处理、不阻塞主链路；避免大数据拷贝与遍历；对象复用、内存池；算法优化降低时间复杂度；
- **并发与锁**：大锁拆小锁；互斥锁改读写锁；串行请求改并行；用 SPSC 无锁队列；
- **架构与语言**：本地缓存放在 Redis 缓存之前；数据预计算。

## 一面 · 向量索引的几种实现形式？

**HNSW**：借鉴跳表思想的分层可导航图索引。按概率把节点分布在多层结构：上层稀疏做长距离快速跳转、下层稠密做精细近邻检索；检索从顶层逐层向下贪心找最近邻直到底层。凭分层跳跃大幅减少检索步数，速度与召回率优异，但**索引内存占用高、构建开销大**。

**IVF**：基于 K-Means 聚类分桶的向量倒排索引。先把全量向量聚成 `nlist` 个聚类桶并建立倒排表；检索时只取离查询向量最近的 `nprobe` 个桶内部遍历，输出 topk，不用全量扫描。`nlist` 按向量总数开根号×4 经验设置；`nprobe` 越大召回越高、速度越慢——两者是**速度与精度的取舍**。

**对比**：HNSW 精度高查询快，构建慢吃内存，适合百万级以下数据；IVF 构建快省内存、查询精度略低、吞吐快（内存连续规整、缓存命中多、并发抗压强），适合百万级以上数据。

## 一面 · 请求提交到主节点、还没同步到从节点主节点就挂了，Raft 怎么做？

- 新提交的日志从节点看不到也不会执行，剩余从节点的日志少于主节点；
- 剩余 follower 开始选举并选出**新主节点**；
- 一段时间后旧主恢复，通过 WAL 机制恢复了挂机前提交但未分发的日志，发现集群已有新主、任期比自己大，**降级为 follower**；
- 旧主接收到新主心跳后被动做日志对比，发现日志冲突，**主动截断自己的多余日志**，再慢慢对齐下线期间缺失的日志。

**总结**：先前提交的请求并没有成功——没同步到多数节点，客户端可以超时重试；旧主下线期间的日志上线后会慢慢和新主对齐。

## 一面 · perf 火焰图这类工具用过吗？

目前没有（WSL2 一直装不上 perf）。火焰图的**横向宽度代表 CPU 耗时占比**，一眼能看出哪个函数是瓶颈——死循环、锁竞争、频繁系统调用或内核 IO 开销。和 top、pstack 这类瞬时工具比，它是**全局采样统计的动态分析**，适合快速定位性能瓶颈、做深度调优。

## 一面 · 平时怎么检查程序性能瓶颈？

- **pstack**：找进程 id，手动打栈多打几次，观察是否多次停在同一函数——那个就是 CPU 瓶颈，比如大量线程阻塞在锁获取（lock、cond_wait）或系统调用、网络 IO；
- **GDB**：`gdb -p <pid>` → `thread apply all bt`，多采样几次，看大部分线程卡在什么地方；
- **steady_clock 埋点**：函数入口埋点、子流程内部埋点，测算每段耗时；
- **top**：看进程和线程 CPU 占用，可能查出代码逻辑 bug（如死循环）。

## 一面 · 导致系统慢的可能性？

系统调用频繁；缺页中断；数据库频繁刷盘或文件读写 IO；网络 IO 瓶颈；内存分配瓶颈；锁竞争；大数据遍历；计算密集型瓶颈。

## 一面 · 怎么排查锁竞争和死锁？

**排查**：`pstack <pid>` 看是否大量线程在等待加锁、被唤醒；`gdb -p <pid>` / `thread apply all bt` 直接看卡点。

**优化方案**：减少锁的范围与不必要的锁结构；改用无锁结构（SPSC 无锁缓冲区、atomic 原子变量）；分段锁优化加锁策略；用读写锁替换互斥锁。

**案例**：做 B+ 树数据结构测试时遇到过死锁（迭代器上锁 / 头部页上锁）。朴素输出调试对定位测试样例有用，但找具体是哪一行慢；更直观的还是 gdb / pstack 看卡在哪一行，特定测试案例再用输出调试深入了解。

## 二面 · MySQL 主从用 binlog，为什么大部分数据库一致性改用 Raft？

MySQL binlog 主从**只是日志复制**，只做数据同步：一致性弱、会脑裂、要人工切主、无法写扩展。Raft 是分布式共识协议，优势：

- **强一致**：写必须同步到过半节点才成功，不丢数据、不冲突；
- **自动选主 & 自愈**：主节点挂了自动选举，业务无感知；
- **无单点、可分布式扩展**：支持分片扩写，适合云原生架构；
- **不会脑裂**：靠任期号和日志索引保证唯一主节点；
- 是现代分布式存储、数据库的标准一致性方案。

## 二面 · Raft 怎么处理脑裂？

正常情况下选举必须获得超过半数节点投票，因此分区后**节点较少的一边选不出 leader**。如果原 leader 在多数节点边，没有任何问题，等网络恢复即可。

如果原 leader 在少数节点边：多数派会选出新主、任期增加——此时两边都有 leader，且**两边都能接收提交请求**。但只有日志被节点内的多数节点同步了才算真正提交成功、日志才会增长；少数派那边即使能接收请求，日志也不会增长。

分区结束后，**任期更高的新主继续担任 leader**，旧主降级并删除冲突日志后同步。

## 二面 · 为什么 MySQL 索引用 B+ 树？哈希索引不好在哪？

1. 哈希索引**只能等值匹配**；
2. 哈希把整个索引字段做哈希运算，**无法走最左前缀匹配**，索引生效场景减少；
3. 磁盘遍历不友好，**无法顺序扫描**，只能随机散列查找，不适合批量遍历；
4. 哈希表扩容需要**重新计算所有哈希、迁移数据**，开销很高。

## 二面 · 为什么选型用 Milvus，而不是关系型数据库加向量化插件？

关系型数据库 + 向量插件的短板：数据规模一大性能暴跌、能承受的数据量太小；HNSW 这类索引占内存，**与传统事务资源争抢**导致性能不稳定；不支持向量的自动分片和跨节点检索、依赖插件、扩容迁移故障恢复麻烦；无企业级向量能力（不支持混合检索、无冷热分层、索引类型少、运维靠人工）。

向量数据库专为高维向量检索设计，对内存布局、索引算法深度优化，性能极高；读写互不干扰、支持高吞吐入库；分布式接入能力强、支持冷热分层、向量压缩等企业级功能。

## 二面 · 国产大模型和国外大模型接入 Agent 的差异？

- **工具调用**：国外调用稳定、格式规范容错高；国产简单调用够用，复杂参数容易格式错乱、漏参数；
- **任务规划**：国外擅长长链路复杂任务、反思纠错强；国产只适合短流程，长任务容易断链跑偏；
- **长文本**：国外超长上下文保真度高；国产标称窗口大但长文本易丢细节；
- **语言能力**：国产中文本土化、合规理解更强；国外英文、通用推理、知识面更强；
- **多模态**：国外图文解析、复杂图表识别成熟；国产只能满足基础能力；
- **代码工程**：国外系统操作、代码工程能力极强；国产只能写简单代码、系统级能力弱；
- **合规部署**：国产私有化部署、数据合规安全更强；国外合规偏西方、私有化成本高。

## 二面 · Vibe Coding 有标准流程吗？和 Spec Coding 有何不同？

**Vibe Coding**：意图定义 → AI 生成 → 运行验证 → 自然语言反馈 → 迭代收敛，全程以"效果/氛围"为导向，快速试错、不纠结细节。快但易失控，适合原型 / 小需求。

**Spec Coding**：先写结构化、无歧义的规格文档（接口/字段/约束），AI 严格按 spec 生成。稳但慢，适合工程 / 长线系统。

## 追问 · RAG 文档做切片时怎么处理大表格和图片？

**图片**，三种方案：
1. **多模态模型做向量化**：文字和图片映射到同一维空间，保留视觉信息、布局、图表趋势，不丢原图特征；代价是存储变大、推理开销略高；
2. **OCR + LLM 概括**：先提取文字 → 丢给 LLM 做内容概括 → 纯文本入库切片；
3. **双路索引融合**：图片抽视觉向量存一路索引，OCR + 摘要抽文本向量存一路索引，检索时两路召回合并：文字匹配 + 视觉匹配。

**大表格**：最好转成 Markdown 或 HTML 文件——LLM 对格式化文本的语义理解更好，MD 表格语法规整、行列边界清晰。用 pdfplumber / docx 等库本地规则解析 → 自动转标准 Markdown 表格 → 结构化切片：小表格整张表作为一个切片单元；超大长表格按"表头 + N 行数据"分块切片，保证每块都带表头、不丢上下文。表格非常复杂、严重倾斜或模糊导致 OCR 无法解析时，需要翻译成业务语言再用 LLM。

## 追问 · 哪些情况会导致 MySQL 主从同步延迟大？

1. **主库产生大量 binlog**：超大事务（批量数据变更、表结构迁移、写入压力大）都会产生大量 binlog——binlog 等事务完成后传到从库、从库才开始回放，且回放过程很长，导致延迟；
2. **从库侧**：从库和主库系统资源不一致，从库跟不上主库执行速度；从库还要抗读压力，读写一体会让 CPU 压力更大；
3. **网络与架构**：主从网络延迟较大，比如跨机房、跨地域、网络丢包。

## 追问 · 怎么解决主从延迟？

- 从库**并行复制**、并行回放 binlog；
- 保证主从表**索引一致**，避免从库 SQL 全表扫描；
- **拆分大事务**，禁止超大事务一次性提交；
- 机器部署尽可能**同机房**，减少网络传输延迟与波动；
- **拆分读流量**，避免单节点读压力过大占满 CPU。

## 追问 · 怎么拆分大事务？

大事务危害：binlog 巨大、回放慢、锁持有时间长、主从延迟、死锁、回滚代价高。

- delete / update 可以**分批次提交**、循环分批执行；
- 事务内只保留增删改；查询、业务计算、接口调用等设计计算 IO 的操作全部放到**事务外边**；
- 无强一致性要求时，可以把多张表更新**拆成独立小事务**。

## 追问 · MySQL 怎么查死锁？

`show engine innodb status;` 查看 InnoDB 引擎当前锁、事务、死锁信息。输出里找 **LATEST DETECTED DEADLOCK** 区块，记录：两个冲突事务分别执行的 SQL、各自持有/等待的锁与锁类型及行记录、最终被回滚的事务。
