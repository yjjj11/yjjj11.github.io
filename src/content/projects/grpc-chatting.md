## 项目简介

一个聊天室从单机到集群、再到动态扩缩容的完整架构演变。核心矛盾始终是两点：**历史消息怎么持久化**、**高并发连接怎么分散**——每一轮演进都是在解决上一轮暴露的问题。

## 架构演变

**① 单机 + Redis**：一个客户端一个服务器，历史消息靠 Redis 持久化。问题：Redis 是内存键值库，快速原型阶段可用，但机器一重启就丢失历史消息，需要磁盘持久化。

**② 服务端 + SQLite**：快速开发期选最简单的方案，SQLite 依附在服务端，服务端包揽消息转发与存储。问题：并发连接一多全部打到同一台机器，大量网络 IO 和消息转发高度占用 CPU，性能大幅下降。

**③ 集群化部署**：扩展到多机器，每台接收一定数量连接，分散连接压力到不同主机。通过提前配置其他主机的 ip:port 完成集群初始化，消息在不同服务器间转发。问题：集群要预先配置好所有节点，**无法动态扩容**——访问量暴增时要水平扩展但配置要改并重启，造成一段不可用时间。

**④ Redis pub/sub 服务注册 + Nginx L4 负载均衡**：实现动态扩缩容的最小改动方案——新网关节点上线时自注册，通知集群有新服务上线；服务层前面加一层 Nginx stream L4 负载均衡接入流量。问题：此时持久化仍是 SQLite，**每台服务器各带一份数据**，全局消息不同步、顺序可能被打断。

**⑤ 存储拆分 + MySQL**：
- 先把 SQLite 单独拆成一个服务模块，所有服务器的存储请求通过 RPC 发给它串行执行。压测：RPC 单机 echo 服务 20k qps，但最大在线消息转发只有 170 msg——多服务器单存储层只能串行存储成为瓶颈（一次消息转发一次持久化，调用频繁、锁竞争严重）。
- 将存储从 SQLite 迁到 MySQL，利用可并发读写解决锁竞争；**一消息一存改为批量异步存**，减少 RPC 往返；存储模块只负责读，数据库写操作内嵌到转发服务器；把读请求的发起与返回拆分到独立模块减少消息转发服务 CPU 占用。测试：单机多并发下最大消息转发 qps 约 4000~6000，相比原来提升明显。

**⑥ 五节点压测仍未达预期**（qps 只有 ~11.5K），排查出三个瓶颈：
- **MySQL 写锁竞争**（读写合计约 13.8K qps 是上限）；
- **Nginx 负载不均**——所有消息流量实际只走了 5 节点中的 1~2 个；
- **Redis 单点**——每条消息产生 1 次 INCR（seq_id）+ 1 次 HGET（user_location 路由），单节点 ~11K qps 时 Redis 总命令数约 109K ops/sec，已接近单核瓶颈。

**优化**：将 Redis 剥离出消息转发服务，消息 id 改用本地雪花算法生成，用户 location 只在刚上线时由服务节点缓存一份；给 MySQL 表加索引提升查询速度；解决 Nginx 负载不均衡，换短连接池压测。结果 qps 依然 ~13K，提升不大——说明在压测链路里总会有新的瓶颈浮出，需要持续系统性排查。

## 核心结论

聊天室高并发的关键在于：**存储与转发职责分离、批量异步化、去掉中间件单点、均衡负载**。同时这个项目也展示了性能调优的常态——修完一个瓶颈总会暴露下一个，衡量的是链路里最弱的环节。
